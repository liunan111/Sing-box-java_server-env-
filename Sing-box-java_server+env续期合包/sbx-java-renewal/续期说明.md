- env.txt：就是你上传的那份，已填好的 21 项变量原样未动，

## 先说清楚：这个和上次的 nodejs 改版不一样
上次 nodejs-argo 能把 cloudflared 下载源直接换成官方，是因为
cloudflared 的下载地址就写在 index.js 里。这次这个 jar 我反编译
查过了，情况不同：

- server.jar 里只有一个类 SbxService，里面**没有 cloudflared、
  没有版本号、没有 cloudflared 的下载地址**。
- 它启动时只做一件事：按系统架构从作者镜像下载一个核心程序
  sbx（amd64：amd64.ssss.nyc.mn/s-box，arm64：arm64.ssss.nyc.mn/s-box），
  存到系统临时目录（java.io.tmpdir）下的 sbx 文件，然后把你
  env.txt 里的变量全部传给这个 sbx 去跑。
- 关键在缓存逻辑：**如果临时目录里已经有 sbx，它就直接用旧的，
  不重新下载**。所以同一台容器光点重启，核心永远是旧的，
  核心里带的 cloudflared 也就永远是旧版——这就是为什么你
  光重启解决不了。

结论：jar 这一层改不到 cloudflared，只能改“是否重新下载核心”
这一步。cloudflared 到底是新是旧，取决于作者镜像里那个
sbx 核心本身有没有更新。

## 这个包做了什么
只加了一个启动器 ForceRefresh，原版 SbxService.class 一个字节
都没动（已核对字节一致），启动命令还是 java -jar server.jar，
Java 版本要求也不变（原版和启动器都是 Java 17 的 class 版本）。

启动器逻辑：
- 只有当 FORCE_REFRESH_SBX=true 时，才先删掉临时目录里的
  缓存 sbx，然后原样调用 SbxService.main，让它重新从作者镜像
  下载最新 s-box。
- 没有这个开关时，行为和原版完全一样，不会每次重启都重新下载。

开关两种写法都认（任选一种）：
- 平台环境变量里加：FORCE_REFRESH_SBX=true
- env.txt 里加一行：export FORCE_REFRESH_SBX=true

## 部署步骤（续期用一次）
1. 备份你现在的部署，先记好你那份 env.txt（见上面安全提醒）。
2. 用本包里的 server.jar 替换掉原来的 server.jar，
   启动命令不变：java -jar server.jar。
   本包里的 env.txt 就是你原来的那份，解压后直接用它，
   不用再替换。
3. 在 env.txt 里加一行 export FORCE_REFRESH_SBX=true，部署/启动一次。
4. 去 Cloudflare 后台隧道列表，看这条隧道的「版本」列。
5. 确认后，把那行改回 false 或删掉，再正常重启一次，
   恢复成缓存模式。以后想再续期，再把开关加回来就行。

## 诚实上限：这个包保证什么、不保证什么
保证：本次启动一定重新下载作者镜像里最新的 s-box（不再用旧缓存）。
不保证：Cloudflare 版本列一定变成 2026.10.3。

- 如果版本列变成了新版（例如 2026.10.x），说明作者那边
  s-box 已经更新了，续期成功。
- 如果续期启动后版本列还是 2025.11.1，说明作者镜像里的
  s-box 本身还没更新 cloudflared——这种情况下任何 jar 层面的
  改法都变不出新版，只能等作者更新 s-box，或者改用上次
  那个 nodejs-argo 改版包（那个是直接从 Cloudflare 官方拉
  cloudflared，能确定是最新版）。

## 已实测 / 未实测（说清楚）
已实测：
- 启动器逻辑（用替身程序验证，不跑真实服务）：有开关时
  删缓存并转交给原 main；无开关时保留缓存；环境变量和
  .env 两种开关写法都通过。
- 新 jar 结构：包含原版 SbxService.class（字节一致）+
  ForceRefresh.class，清单 Main-Class=ForceRefresh，两个类
  都是 Java 17 版本。
未实测：
- 没有在你平台上实跑这个 jar 的完整服务。实跑会下载并运行
  作者的 sbx 核心、并用你的密钥建立隧道，不能在测试机上
  这么干，所以最终版本以你部署后 Cloudflare 后台显示的为准。
